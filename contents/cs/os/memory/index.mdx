- 프로세스는 많고 물리 RAM은 한정 → OS가 메모리를 **나눠 쓰고 격리**
- 핵심 아이디어 = **가상 메모리** → 각 프로세스에 "혼자 다 쓰는 듯한" 주소 공간 제공

## 책상과 책장으로 이해하기

- **책상(RAM)** 은 작고, **책(데이터)** 은 많음
- 자주 보는 책만 책상에 올려두고, 나머지는 **책장(디스크)** 에 둠
- 필요한 책이 책상에 없으면 → 책장에서 꺼내옴 (이게 **page fault**)
- 책상이 꽉 차면 → 안 보던 책을 책장에 도로 넣음 (이게 **page replacement**)

<KeyPoint title="이 비유의 핵심">
RAM이 부족해도 디스크를 보조로 써서 **RAM보다 큰 메모리**를 쓰는 것처럼 동작 ·
"필요한 것만 RAM에" 올리는 게 가상 메모리의 아이디어
</KeyPoint>

## 가상 메모리와 주소 변환

- 프로세스는 **가상 주소**만 봄 → MMU가 **물리 주소**로 변환
- 메모리를 **페이지(page)** 라는 일정 크기(보통 4KB) 조각으로 나눠 관리

```mermaid
flowchart LR
    VA["가상 주소<br/>페이지 번호 + 위치"] --> PT["🗂️ 페이지 테이블<br/>(번호 → 프레임 매핑)"]
    PT --> PA["물리 주소<br/>프레임 번호 + 위치"]
    PA --> RAM["🧠 물리 RAM"]
```

- **페이지 테이블** = "가상 페이지가 RAM 어느 칸(프레임)에 있나"를 적어둔 표

<KeyPoint title="가상 메모리가 주는 것">
- **격리** → 프로세스끼리 서로 메모리 못 건드림 (각자 주소 공간)
- **큰 공간** → 일부만 RAM, 나머지는 디스크 → RAM보다 크게 사용
- **효율** → 실제 쓰는 페이지만 RAM에 올림
</KeyPoint>

## 페이지 폴트

- 접근한 페이지가 RAM에 없을 때 발생 → OS가 디스크에서 가져옴

<Timeline>
<TimelineItem title="1. 접근">
프로세스가 어떤 주소 접근 → 페이지 테이블 확인
</TimelineItem>
<TimelineItem title="2. 없음 발견">
해당 페이지가 RAM에 없음 → page fault 발생
</TimelineItem>
<TimelineItem title="3. 가져오기">
OS가 디스크에서 그 페이지를 빈 칸(프레임)에 올림 · 빈 칸 없으면 **교체**
</TimelineItem>
<TimelineItem title="4. 재시도">
페이지 테이블 갱신 → 멈췄던 작업 다시 실행 (이번엔 성공)
</TimelineItem>
</Timeline>

<Note type="warning" title="page fault는 느리다">
- 디스크 접근은 RAM보다 **수만 배** 느림 → page fault 잦으면 성능 폭락
- 그래서 "자주 쓰는 페이지를 RAM에 잘 유지"하는 게 중요
</Note>

## 페이지 교체 알고리즘

- RAM(책상)이 꽉 참 → 어떤 페이지를 내보낼지(victim) 고르기

| 알고리즘 | 어떤 걸 내보내나 | 특징 |
|------|------|------|
| **FIFO** | 가장 먼저 들어온 것 | 단순 / 가끔 이상하게 더 나빠짐(Belady) |
| **Optimal** | 앞으로 가장 늦게 쓸 것 | 이론상 최고지만 미래를 알아야 → 불가능 |
| **LRU** | 가장 오래 안 쓴 것 | 실전에서 잘 맞음 / 구현 비용 ⬆️ |
| **Clock** | LRU 근사 | 비트 하나로 싸게 LRU 흉내 |

<Note type="note" title="LRU가 잘 맞는 이유">
- **지역성**: 방금 본 데이터를 또 볼 확률이 높음 (반복문·최근 파일 등)
- 그래서 "가장 오래 안 본 것"을 버리면 적중률이 높음 = LRU
- 진짜 LRU는 무거워서 실무는 보통 **Clock**(LRU 근사)
</Note>

## TLB

- 매번 페이지 테이블 뒤지면 느림 → 자주 쓰는 변환 결과를 **TLB**(작은 캐시)에 저장
- TLB에 있으면(hit) 바로 변환 / 없으면(miss) 페이지 테이블 조회

## 스래싱

<Note type="warning" title="스래싱 (Thrashing)">
- RAM이 너무 부족 → page fault·교체가 **쉴 새 없이** 일어남 → CPU가 페이지 옮기느라 정작 일을 못 함
- 증상: CPU 사용률은 낮은데 디스크는 미친 듯이 돌아감
- 해결: RAM 늘리기 · 동시에 도는 프로세스 수 줄이기 · 자주 쓰는 페이지 묶음(working set) 확보
</Note>

<Note type="pink" title="정리">
- 가상 메모리 = 책상(RAM) + 책장(디스크), 필요한 것만 책상에
- 주소 변환: 가상(페이지) → 페이지 테이블 → 물리(프레임), TLB로 가속
- 없으면 page fault → 디스크에서 로드, 꽉 차면 교체(LRU/Clock)
- 교체가 과하면 스래싱 → RAM·프로세스 수 조절
</Note>
