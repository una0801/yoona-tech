- **정규화** → 중복 없게 표를 **잘게 쪼개 정리** · 한 사실은 한 곳에만
- 핵심 한 문장 → "같은 값을 여러 곳에 적어두면 **수정할 때 지옥**"
- 단계 → 1NF → 2NF → 3NF → BCNF로 갈수록 **중복·이상현상 제거**
- 트레이드오프 → 너무 쪼개면 JOIN 폭증 → 일부러 합치는 **반정규화**도 존재

## 주소록 한 칸에 다 적으면 생기는 일

- 친구 정보를 메모장 표 한 줄에 "이름·전화·회사·회사주소" **다 욱여넣음**
- 같은 회사 동료가 5명이면 → 회사주소를 **5번 똑같이** 적음
- 회사가 이사 가면 → 5줄을 **전부 손으로 수정** · 한 줄 빠뜨리면 데이터 깨짐
- 정규화 → "회사" 표를 따로 빼서 → 회사주소는 **딱 한 번만** 적고 참조

<KeyPoint title="이 비유에서 가져갈 것">
정규화 = 중복을 없애려고 표를 쪼개는 작업 ·
이상현상 = 중복 때문에 INSERT·UPDATE·DELETE가 꼬이는 사고 ·
함수 종속 = "이 값이 정해지면 저 값도 자동으로 정해진다"는 관계
</KeyPoint>

## 정규화 안 한 테이블의 3가지 이상현상

- 주문 정보를 한 테이블에 다 때려넣은 비정규 테이블 가정

| order_id | customer | product_id | product_name | price | qty |
|---|---|---|---|---|---|
| 1 | 김철수 | P10 | 키보드 | 30000 | 2 |
| 1 | 김철수 | P11 | 마우스 | 15000 | 1 |
| 2 | 이영희 | P10 | 키보드 | 30000 | 1 |

<Cards cols={3}>
<Card icon="➕" title="Insert Anomaly 삽입 이상">
아직 **주문 없는** 신상품을 등록하려면? · order_id가 없어 행을 못 넣음 · 상품만 따로 등록 불가
</Card>
<Card icon="✏️" title="Update Anomaly 수정 이상">
키보드 가격 30000→35000 변경 시 · product_name·price가 **여러 행에 중복** · 일부만 고치면 값 불일치
</Card>
<Card icon="🗑️" title="Delete Anomaly 삭제 이상">
order_id 2를 지우면? · 그 행에만 있던 **상품 정보까지 같이 증발** · 지우면 안 될 게 같이 삭제
</Card>
</Cards>

<Note type="warning" title="이상현상의 뿌리">
- 원인 → 서로 다른 주제(주문·고객·상품)를 **한 테이블에 섞음**
- 같은 사실(상품가격)이 **여러 행에 중복 저장** → 수정·삭제 시 불일치·소실
- 해결 → 주제별로 표를 쪼개고 함수 종속을 따라 분리 = 정규화
</Note>

## 함수 종속 - 무엇이 무엇을 결정하는가

- **함수 종속 (Functional Dependency)** → `X → Y` · X가 정해지면 Y가 **유일하게** 결정됨
- 예 → `product_id → product_name, price` · 상품ID 정해지면 이름·가격 자동 결정
- 예 → `(order_id, product_id) → qty` · 주문+상품 조합이 정해져야 수량 결정

```text
product_id → product_name, price      (상품ID가 이름·가격 결정)
order_id   → customer                 (주문ID가 고객 결정)
(order_id, product_id) → qty          (복합키가 수량 결정)
```

- **부분 함수 종속** → 복합키 **일부**만으로 결정 (예: order_id만으로 customer 결정) → 2NF 위반
- **이행 함수 종속** → `A → B → C`로 **간접** 결정 (예: order → customer → customer_grade) → 3NF 위반

## 단계별 분해 - 표가 어떻게 쪼개지나

<Timeline>
<TimelineItem title="1NF (제1정규형) · 원자값">
모든 칸이 **하나의 값** · 한 칸에 "키보드, 마우스" 같은 다중값·반복그룹 금지 · 위 테이블은 이미 1NF 충족
</TimelineItem>
<TimelineItem title="2NF (제2정규형) · 부분 종속 제거">
복합키 **일부**에만 종속된 컬럼 분리 · `order_id → customer`, `product_id → name,price`를 별도 표로 · 기본키 전체에 완전 종속만 남김
</TimelineItem>
<TimelineItem title="3NF (제3정규형) · 이행 종속 제거">
키가 아닌 컬럼이 다른 **비키 컬럼**을 결정하면 분리 · `customer → customer_grade`면 grade를 customer 표로
</TimelineItem>
<TimelineItem title="BCNF (보이스-코드 정규형) · 결정자=후보키">
모든 결정자(X→Y의 X)가 **후보키**여야 함 · 3NF인데 결정자가 후보키가 아닌 드문 경우까지 제거 · 3NF의 강화판
</TimelineItem>
</Timeline>

### 2NF 적용 결과 (표 분리)

- `orders` → 주문과 고객

| order_id | customer |
|---|---|
| 1 | 김철수 |
| 2 | 이영희 |

- `products` → 상품 마스터 (가격 중복 제거)

| product_id | product_name | price |
|---|---|---|
| P10 | 키보드 | 30000 |
| P11 | 마우스 | 15000 |

- `order_items` → 주문-상품 연결 + 수량

| order_id | product_id | qty |
|---|---|---|
| 1 | P10 | 2 |
| 1 | P11 | 1 |
| 2 | P10 | 1 |

<Note type="success" title="분리 후 이상현상 해소">
- 삽입 → 주문 없어도 `products`에 신상품 단독 등록 가능
- 수정 → 키보드 가격은 `products` **한 행만** 변경 → 전 주문에 즉시 반영
- 삭제 → 주문 1건 지워도 상품 마스터는 그대로 보존
</Note>

```sql
-- 3NF 결과 스키마 + FK
CREATE TABLE products (
  product_id   VARCHAR(10) PRIMARY KEY,
  product_name VARCHAR(50) NOT NULL,
  price        INT NOT NULL
);
CREATE TABLE orders (
  order_id  INT PRIMARY KEY,
  customer  VARCHAR(30) NOT NULL
);
CREATE TABLE order_items (
  order_id   INT,
  product_id VARCHAR(10),
  qty        INT NOT NULL,
  PRIMARY KEY (order_id, product_id),
  FOREIGN KEY (order_id)   REFERENCES orders(order_id),
  FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

## 정규화 vs 반정규화 - 트레이드오프

<ProsCons>
<Pros title="정규화 (쪼개기)">
- 중복 제거 → 저장공간 절약
- 이상현상 차단 → 데이터 무결성
- 수정 한 곳만 → 일관성 유지
- 단점 → JOIN 많아짐 → 조회 느려질 수 있음
</Pros>
<Cons title="반정규화 (일부 합치기)">
- JOIN 줄여 **읽기 성능** 확보
- 집계값·자주 쓰는 값 미리 저장
- 단점 → 중복 발생 → 갱신 시 동기화 책임 증가
- 단점 → 이상현상 재발 위험 → 앱·트리거로 관리
</Cons>
</ProsCons>

<Note type="pink" title="실무 판단 기준">
- 기본 → **3NF까지 정규화** 후 시작 → 무결성 우선
- 조회 병목 확인되면 → 그 지점만 **선택적 반정규화** (예: 주문 테이블에 상품명 사본 캐시)
- 반정규화 시 → 원본 변경 시 사본 동기화 로직 **반드시** 동반 (트리거·배치·앱 레벨)
- 통계·리포트성 집계는 → 별도 집계 테이블·읽기 전용 복제본으로 분리도 고려
</Note>
