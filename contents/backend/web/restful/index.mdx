## REST 란?
- **Representational State Transfer** 의 약자
- HTTP 프로토콜 위에서 동작하는 **아키텍처 스타일**
- 자원을 **리소스(Resource)** 단위로 표현하고, 클라이언트가 표준화된 방식으로 접근하도록 설계
---

## Resource
- **리소스 = 서비스에서 관리해야할 대상**
- 모든 것은 리소스로 간주 : 사용자(User), 주문(Order), 게시글(Post), 상품(Product) 등
- 리소스는 **명사**로 표현해야함
- 예시
```
- `/users` → 사용자 집합
- `/users/123` → 특정 사용자
- `/orders/2024` → 특정 주문
```
- 원칙
  - URI에 동사가 아닌 **명사** 사용 (`/getUsers` ❌ → `/users` ✅)
  - 계층적 구조 사용 (`/users/123/orders/456`)
---

## URI
- Uniform Resource Identifier
- **리소스를 식별**하는 주소
- 직관적이고, 일관성 있게 설계
- 규칙
```
1. **소문자 사용**  
   - `/users`, `/products` ✅  
   - `/Users`, `/Products` ❌
2. **복수형 사용**  
   - `/users` → 사용자 컬렉션
   - `/users/1` → 특정 사용자
3. **계층적 관계 표현**  
   - `/users/1/orders/5` → 특정 사용자의 특정 주문
4. **쿼리 파라미터는 필터링/검색용**  
   - `/users?active=true&sort=created_at`
```
---
## HTTP Method
- 리소스에 대한 행위는 **HTTP 메서드**로 표현

| Method   | 의미 | 예시 |
|----------|------|------|
| **GET**  | 리소스 조회 | `GET /users/1` → ID=1인 사용자 조회 |
| **POST** | 리소스 생성 | `POST /users` → 새 사용자 생성 |
| **PUT**  | 리소스 전체 수정 (대체) | `PUT /users/1` → ID=1 사용자 전체 업데이트 |
| **PATCH**| 리소스 부분 수정 | `PATCH /users/1` → ID=1 사용자 일부 필드만 수정 |
| **DELETE** | 리소스 삭제 | `DELETE /users/1` → ID=1 사용자 삭제 |

- 메서드 이름을 URI에 넣지 않음 (`/getUser`, `/deleteUser` ❌)

---
## HTTP Status Code
- API 응답은 **상태 코드**로 의미를 명확하게 표현
```
- 200 OK → 요청 성공 (GET, PUT, PATCH 성공)
- 201 Created → 리소스 생성 성공 (POST)
- 204 No Content → 요청 성공했으나 응답 본문 없음 (DELETE)
- 400 Bad Request → 잘못된 요청 (파라미터 오류 등)
- 401 Unauthorized → 인증 실패 (로그인 필요)
- 403 Forbidden → 권한 없음
- 404 Not Found → 리소스 없음
- 409 Conflict → 리소스 충돌 (중복 데이터 등)
- 500 Internal Server Error → 서버 내부 오류
```
- 예시 : 사용자(Users) API 설계

| 행위 | URI | Method | Status Code |
|------|-----|--------|-------------|
| 사용자 목록 조회 | `/users` | GET | 200 |
| 특정 사용자 조회 | `/users/{id}` | GET | 200 / 404 |
| 사용자 생성 | `/users` | POST | 201 |
| 사용자 수정(전체) | `/users/{id}` | PUT | 200 / 404 |
| 사용자 수정(일부) | `/users/{id}` | PATCH | 200 / 404 |
| 사용자 삭제 | `/users/{id}` | DELETE | 204 / 404 |

---
## 정리
1. Resource : 모든 대상을 명사로 표현
2. URI : 직관적이고 계층적, 소문자/복수형 사용
3. HTTP Method : 동작은 메서드로 표현 (GET/POST/PUT/PATCH/DELETE)
4. Status Code : 결과를 명확히 나타내는 코드 사용

> RESTful API의 핵심은 **일관성**과 **표준 준수**
> 누구나 URI만 보고 어떤 동작인지 직관적으로 이해할 수 있어야 함
