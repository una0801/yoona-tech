- **파이프라이닝** → 명령어 하나가 끝나길 기다리지 않고 단계별로 **겹쳐서** 처리
- 명령어 한 개의 시간(지연)은 그대로지만 → 단위 시간당 처리량(throughput) 쭉 ⬆️
- 공짜는 아님 → 단계끼리 의존·분기 때문에 **해저드** 발생 → 멈춤(stall) 생김

## 세탁기-건조기로 이해하기

- 빨래 4더미 · 각 더미가 **세탁 → 건조 → 개기** 3단계
- 순차 방식 → 1더미 다 끝내고 2더미 시작 → 세탁기 돌 동안 건조기 **놀고 있음**
- 파이프라인 → 1더미 건조 들어가는 순간 2더미 세탁 시작 → 모든 기계가 **동시에** 일함
- 더미 하나 끝나는 시간은 똑같지만 → 전체 빨래 끝나는 시간이 확 줄어듦

<KeyPoint title="이 비유에서 가져갈 것">
파이프라인 = 단계를 겹쳐 모든 처리 장치를 항상 바쁘게 ·
명령어 하나의 지연(latency)은 안 줄지만 · 줄줄이 들어올 때 처리량(throughput)이 크게 ↑
</KeyPoint>

## 5단계 파이프라인

- 전형적 RISC CPU → 명령어를 다섯 단계로 쪼갬 · 각 단계는 전용 회로 담당

<Layers>
<Layer title="IF" sub="Instruction Fetch" color="sky">
메모리에서 명령어 꺼내옴 · PC(프로그램 카운터)가 가리키는 주소 읽기
</Layer>
<Layer title="ID" sub="Instruction Decode" color="violet">
명령어 해석 · 어떤 연산인지 파악 · 레지스터에서 피연산자 읽기
</Layer>
<Layer title="EX" sub="Execute" color="green">
ALU가 실제 계산 · 덧셈·비교·주소 계산 수행
</Layer>
<Layer title="MEM" sub="Memory Access" color="amber">
메모리 읽기/쓰기 · load·store 명령만 실제로 접근
</Layer>
<Layer title="WB" sub="Write Back" color="pink">
계산 결과를 레지스터에 기록 · 다음 명령어가 쓸 수 있게 반영
</Layer>
</Layers>

```mermaid
flowchart LR
    IF["IF<br/>명령어 가져오기"] -->|디코드 넘김| ID["ID<br/>해석·레지스터 읽기"]
    ID -->|연산 넘김| EX["EX<br/>ALU 계산"]
    EX -->|주소·데이터| MEM["MEM<br/>메모리 접근"]
    MEM -->|결과 넘김| WB["WB<br/>레지스터 기록"]
```

## 클럭 인터리빙 (단계 겹치기)

- 한 클럭마다 각 명령어가 한 칸씩 전진 → 같은 시점에 서로 다른 단계 동시 진행
- 명령어 I1~I5가 클럭 T1~T9에 어떻게 겹치는지

| 명령어 | T1 | T2 | T3 | T4 | T5 | T6 | T7 | T8 | T9 |
|--------|----|----|----|----|----|----|----|----|----|
| I1 | IF | ID | EX | MEM | WB |    |    |    |    |
| I2 |    | IF | ID | EX | MEM | WB |    |    |    |
| I3 |    |    | IF | ID | EX | MEM | WB |    |    |
| I4 |    |    |    | IF | ID | EX | MEM | WB |    |
| I5 |    |    |    |    | IF | ID | EX | MEM | WB |

- T5 시점 → I1=WB · I2=MEM · I3=EX · I4=ID · I5=IF → **5개 단계가 한 클럭에 동시 가동**
- 파이프 채워진 뒤(T5~)부터 → 매 클럭마다 명령어 **하나씩 완료** → 이상적 처리량 1 IPC

## 해저드 — 파이프가 멈추는 이유

<Cards cols={3}>
<Card icon="🔗" title="Data Hazard">
앞 명령 결과를 뒤 명령이 곧바로 필요 · WB 전이라 아직 값 없음 · `R1 = R2+R3` 직후 `R4 = R1+R5`
</Card>
<Card icon="🔀" title="Control Hazard">
분기(if·jump) 결과 나오기 전에 다음 명령 미리 가져옴 · 틀리면 가져온 거 다 버림
</Card>
<Card icon="🚧" title="Structural Hazard">
같은 하드웨어 자원을 두 단계가 동시에 원함 · 메모리 포트 1개를 IF와 MEM이 다툼
</Card>
</Cards>

<ProsCons>
<Pros title="해결책 — 막힘 줄이기">
- 포워딩(forwarding) → EX 결과를 WB 안 기다리고 다음 EX로 바로 전달
- 명령어 재배치 → 의존 없는 명령을 사이에 끼워 stall 메움
- 자원 복제 → 명령어 캐시·데이터 캐시 분리로 structural hazard 제거
- 분기 예측 → control hazard에서 다음 명령 미리 추측 실행
</Pros>
<Cons title="해결 못 하면">
- stall(거품) 삽입 → 빈 클럭 만들어 의존 해소될 때까지 대기
- 분기 예측 실패 → 파이프 통째로 비우고(flush) 처음부터 다시
- 깊은 파이프일수록 flush 손해 ⬆️ (버릴 단계가 많음)
</Cons>
</ProsCons>

## 분기 예측 (Branch Prediction)

- 분기 명령 → "참이면 A로, 거짓이면 B로" → 어느 쪽일지는 EX 끝나야 확정
- 그때까지 기다리면 파이프 빔 → CPU가 **미리 한쪽을 추측**해 계속 채워 넣음

<Timeline>
<TimelineItem title="1. 예측">
분기 만나면 과거 기록(같은 분기 최근 결과) 보고 taken/not-taken 추측
</TimelineItem>
<TimelineItem title="2. 투기 실행">
추측한 경로 명령들을 미리 파이프에 채워 실행 (결과는 아직 확정 안 함)
</TimelineItem>
<TimelineItem title="3-A. 적중">
실제 결과 = 예측 → 그대로 진행 · stall 없음 · 손해 0
</TimelineItem>
<TimelineItem title="3-B. 실패">
실제 결과 ≠ 예측 → 미리 채운 명령 전부 flush · 올바른 경로로 다시 채움 (페널티)
</TimelineItem>
</Timeline>

## 처리량 vs 지연 — 헷갈리지 말 것

<Compare>
<CompareCol title="⏱️ Latency (지연)" subtitle="명령어 1개 소요 시간" color="amber">
- 명령어 하나가 IF~WB 다 거치는 시간
- 파이프라인 써도 **줄지 않음** (단계 수 동일)
- 오히려 단계 분할 오버헤드로 살짝 ↑ 가능
</CompareCol>
<CompareCol title="🚀 Throughput (처리량)" subtitle="단위 시간당 완료 개수" color="green">
- 매 클럭 명령어 1개씩 쏟아짐
- 파이프라인의 진짜 이득은 **여기**
- 줄줄이 들어올수록 효과 극대화
</CompareCol>
</Compare>

<Note type="warning" title="깊은 파이프의 함정">
- 단계를 잘게 쪼갤수록(깊은 파이프) → 클럭 속도는 올리기 쉬움
- 그러나 분기 예측 실패 1회 페널티 ⬆️ (버릴 단계가 많아짐)
- 의존성 많은 코드에선 stall·flush 잦아져 → 깊은 파이프가 오히려 손해
</Note>

<Note type="pink" title="실무에서 와닿는 지점">
- 분기 많은 코드(불규칙 `if`·가상함수 호출) → 예측 실패로 느려짐 → 핫루프는 분기 줄이기·분기 없는 코드(branchless)로 최적화
- 데이터 의존 체인이 길면 → 포워딩으로도 못 메워 stall → 독립 연산 섞어 ILP(명령어 수준 병렬성) 확보
- 정렬된 배열 분기가 안 정렬된 것보다 빠른 유명 현상 → 분기 예측 적중률 차이 때문
</Note>
