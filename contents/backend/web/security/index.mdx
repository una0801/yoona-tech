## CORS
- Cross-Origin Resources Sharing
- 브라우저의 **동일 출처 정책(Same-Origin Policy, SOP)**을 완화하기 위한 표준 메커니즘
- 기본적으로 브라우저는 **다른 출처의 리소스 요청을 차단**
- CORS는 서버가 **특정 출처를 허용**하여 교차 출처 요청을 안전하게 수행하도록 함
- 예시 
  - `https://example.com` → `https://api.example.com` 호출 시 CORS 필요
  - 서버 응답 헤더
   ```
   Access-Control-Allow-Origin: https://example.com

   Access-Control-Allow-Methods: GET, POST
   ```
- 주의
  - `Access-Control-Allow-Origin: *`은 개발은 편하지만 인증/쿠키를 포함하는 요청에는 보안상 위험
  - **인증이 필요한 요청**은 반드시 **정확한 Origin**을 지정

## CSRF
- Cross-Site Request Forgery
- 사용자가 인증된 상태에서 **공격자가 의도한 요청을 강제로 실행**시키는 공격
  - ex) 사용자가 은행 사이트 로그인 상태에서 공격자가 만든 페이지 열면 -> 은행에 이체요청이 자동 전송
- 브라우저는 쿠키를 자동으로 전송하기 때문에 공격자는 사용자의 인증 세션을 악용할 수 있음
- 방어 방법
  - **CSRF Token** : 서버가 핸덤 토큰 발급 -> 폼/요청에 포함 -> 서버에서 검증
  - **SameSite Cookie 옵션** : `Set-Cookie: session=...; SameSite=Strict` (외부 사이트에서 오는 요청에는 쿠키가 전송되지 않음)
  - **Referer/Origin 검사**
    - 요청 헤더의 `Origin` 또는 `Referer`가 신뢰할 수 있는 출처인지 확인

## HTTPS
- HTTP + TLS(SSL) 암호화
- 클라이언트와 서버 간 데이터를 **암호화, 무결성, 인증** 보장
- 장점
  - **기밀성** : 통신 데이터 암호화 (패킷 스니핑 방지)
  - **무결성** : 데이터 변조 방지 (MITM 공격 방지)
  - **인증** : 서버 인증서로 신뢰할 수 있는 서버와 통신 보장
- 주요 요소
  - **TLS 핸드셰이크** : 클라이언트-서버가 암호화 키 교한
  - **인증서** : CA(인증기관)가 발급, 브라우저는 유효성 검증
  - **강제 HTTPS** : HSTS(HTTP Strict Transport Security)로 모든 요청을 HTTPS로 리다이렉트

## 정리

| 개념   | 문제 상황 | 해결 방법 |
|--------|-----------|------------|
| **CORS** | 브라우저 SOP로 교차 출처 요청 차단 | 서버에서 `Access-Control-Allow-*` 헤더 설정 |
| **CSRF** | 공격자가 사용자의 인증 세션을 악용 | CSRF Token, SameSite Cookie, Origin 검증 |
| **HTTPS** | 평문 통신 → 도청/변조 가능 | TLS 암호화, 인증서 사용 |
