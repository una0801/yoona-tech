Python 3.12, 정렬 알고리즘을 직접 짜서 비교 횟수와 시간 측정

## 확인하고 싶었던 것

- O(n²)와 O(n log n)이 실제로 얼마나 차이 나는지
- 퀵 정렬이 최악에서 O(n²)가 되는 경우
- 삽입 정렬이 거의 정렬된 데이터에서 빨라지는 이유
- 파이썬 `sorted()`가 직접 짠 정렬보다 빠른 이유
- 어떤 정렬을 언제 써야 하는지

## 비교 횟수를 같이 센 이유

- 시간은 돌릴 때마다 조금씩 다름
- 비교 횟수는 몇 번을 돌려도 같음
- 같은 코드를 두 번 돌린 결과

| n | 1차 버블 비교 | 1차 시간 | 2차 버블 비교 | 2차 시간 |
| --- | --- | --- | --- | --- |
| 1000 | 499,500 | 0.023s | 499,500 | 0.023s |
| 2000 | 1,999,000 | 0.100s | 1,999,000 | 0.098s |
| 8000 | 31,996,000 | 1.720s | 31,996,000 | 1.686s |

> 알고리즘끼리 비교할 때는 시간보다 연산 횟수가 더 믿을 만한 기준

## 1. 버블 정렬 vs 병합 정렬

### 버블 정렬

- 옆에 붙은 두 개를 비교해서 왼쪽이 크면 자리 바꿈
- 한 바퀴 돌면 가장 큰 값이 맨 뒤로

`[4, 3, 2, 1]` 손으로 따라가기

```text
1바퀴
[4, 3, 2, 1]  4와 3 비교 → 바꿈
[3, 4, 2, 1]  4와 2 비교 → 바꿈
[3, 2, 4, 1]  4와 1 비교 → 바꿈
[3, 2, 1, 4]  (비교 3번)

2바퀴
[3, 2, 1, 4]  3과 2 비교 → 바꿈
[2, 3, 1, 4]  3과 1 비교 → 바꿈
[2, 1, 3, 4]  (비교 2번)

3바퀴
[2, 1, 3, 4]  2와 1 비교 → 바꿈
[1, 2, 3, 4]  (비교 1번)
```

- 4개: 3 + 2 + 1 = 6번
- 5개: 4 + 3 + 2 + 1 = 10번
- n개: (n-1) + … + 1 = `n(n-1)/2`번

### 병합 정렬

- 반으로 계속 쪼개서 1개짜리로 만듦
- 정렬된 두 줄을 합치면서 정렬

```text
쪼개기
[5, 2, 7, 1, 6, 3, 8, 4]
[5, 2, 7, 1]  [6, 3, 8, 4]
[5, 2] [7, 1]  [6, 3] [8, 4]
[5][2][7][1]  [6][3][8][4]

합치기
1단계  [2, 5] [1, 7]  [3, 6] [4, 8]
2단계  [1, 2, 5, 7]   [3, 4, 6, 8]
3단계  [1, 2, 3, 4, 5, 6, 7, 8]
```

합치기도 공짜는 아님. `[2, 5]`와 `[1, 7]`을 합치는 과정

```text
[2, 5]  [1, 7]   2와 1 비교 → 1 꺼냄
[2, 5]  [7]      2와 7 비교 → 2 꺼냄
[5]     [7]      5와 7 비교 → 5 꺼냄
[]      [7]      남은 7 붙임
```

- 두 줄의 맨 앞끼리만 비교
- 비교 한 번에 숫자 하나가 확정됨
- 그래서 한 단계에서 비교는 n번을 넘지 않음

| 단계 | 합치는 것 | 비교 |
| --- | --- | --- |
| 1단계 | `[5]+[2]` `[7]+[1]` `[6]+[3]` `[8]+[4]` | 4 |
| 2단계 | `[2,5]+[1,7]` `[3,6]+[4,8]` | 6 |
| 3단계 | `[1,2,5,7]+[3,4,6,8]` | 7 |
| 합계 | | 17 |

- 같은 8개를 버블 정렬로 하면 28번

단계 수는 "반으로 몇 번 나누면 1이 되나" = log₂ n

- 8 → 4 → 2 → 1: 3단계
- 16: 4단계
- 1000: 약 10단계 (2¹⁰ = 1024)
- 100만: 약 20단계 (1000 × 1000이라 10 + 10)

> 숫자가 2배가 돼도 단계는 1개만 늘어남
> 전체 일은 n개 × log n 단계 = O(n log n)

### 돌려보기

```python
import random, time


def bubble_sort(a):
    a = a[:]
    cmp = 0
    n = len(a)
    for i in range(n):
        for j in range(n - 1 - i):
            cmp += 1
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
    return a, cmp


def merge_sort(a):
    if len(a) <= 1:
        return a, 0
    mid = len(a) // 2
    left, c1 = merge_sort(a[:mid])
    right, c2 = merge_sort(a[mid:])
    out, i, j, cmp = [], 0, 0, c1 + c2
    while i < len(left) and j < len(right):
        cmp += 1
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out += left[i:] + right[j:]
    return out, cmp


random.seed(42)
print(f"{'n':>6} | {'버블 비교':>12} {'시간(s)':>8} | {'병합 비교':>10} {'시간(s)':>8}")
for n in [1000, 2000, 4000]:
    data = [random.randint(0, 100000) for _ in range(n)]
    t = time.perf_counter(); _, bc = bubble_sort(data); bt = time.perf_counter() - t
    t = time.perf_counter(); _, mc = merge_sort(data); mt = time.perf_counter() - t
    print(f"{n:>6} | {bc:>12,} {bt:>8.3f} | {mc:>10,} {mt:>8.4f}")
```

n이 2배가 될 때 늘어난 배수

| n | 버블 비교 | 버블 시간 | 병합 비교 | 병합 시간 |
| --- | --- | --- | --- | --- |
| 1000 → 2000 | 4.00배 | 4.3배 | 2.23배 | 2.0배 |
| 2000 → 4000 | 4.00배 | 4.2배 | 2.21배 | 2.4배 |
| 4000 → 8000 | 4.00배 | 4.1배 | 2.19배 | 2.0배 |

- 버블
  - 정확히 4배씩
  - 숫자 2배 → 바퀴 수 2배 × 한 바퀴 비교 2배 = 4배
  - 10배면 100배, 1000배면 100만 배
- 병합
  - 2배보다 조금 더 (2.2배)
  - 숫자 2배 → 2배, 단계 1개 추가 → 조금 더
- 시간도 비교 횟수와 같은 비율로 늘어남

100만 개로 늘리면

- 버블: 100만 × 100만 ÷ 2 = 약 5000억 번 (1000개 0.023초 기준으로 6시간 넘음)
- 병합: 100만 × 20단계 = 약 2000만 번
- 약 2만 5천 배 차이

## 2. 퀵 정렬과 피벗

### 퀵 정렬

- 숫자 하나를 피벗(기준)으로 고름
- 피벗보다 작은 건 왼쪽, 큰 건 오른쪽
- 왼쪽과 오른쪽을 같은 방법으로 또 나눔

맨 끝 숫자를 피벗으로 `[5, 2, 7, 1, 6, 3, 4]`

```text
[5, 2, 7, 1, 6, 3, 4]   피벗 4
→ [2, 1, 3]  4  [5, 7, 6]

[2, 1, 3]   피벗 3  → [2, 1]  3  []
[5, 7, 6]   피벗 6  → [5]  6  [7]
[2, 1]      피벗 1  → []  1  [2]

결과 [1, 2, 3, 4, 5, 6, 7]
```

- 피벗 4가 마침 중간값이라 3개, 3개로 반씩 나뉨
- 반씩 나뉘면 병합처럼 log n 단계 → O(n log n)

### 이미 정렬된 배열이면

같은 방법(맨 끝 피벗)으로 `[1, 2, 3, 4, 5]`

```text
[1, 2, 3, 4, 5]   피벗 5  → [1, 2, 3, 4]  5  []   비교 4번
[1, 2, 3, 4]      피벗 4  → [1, 2, 3]  4  []      비교 3번
[1, 2, 3]         피벗 3  → [1, 2]  3  []         비교 2번
[1, 2]            피벗 2  → [1]  2  []            비교 1번
```

- 맨 끝이 항상 가장 큰 값이라 오른쪽이 매번 비어 있음
- 반이 아니라 1개씩만 줄어듦
- 4 + 3 + 2 + 1 = 10번 → 버블과 같은 패턴, O(n²)

### 피벗을 어디서 고를까

처음 떠올린 방법: 가운데 자리 숫자를 피벗으로

- 정렬된 `[1, 2, 3, 4, 5]`에서 가운데는 3
- `[1, 2]  3  [4, 5]`로 반씩 나뉨

실제로 많이 쓰는 방법도 같이 비교

- 끝 피벗: 맨 끝 자리
- 가운데 피벗: 가운데 자리
- 랜덤 피벗: 아무 자리나 무작위

### 돌려보기

```python
import random


def quick_sort(a, pivot_mode="end"):
    a = a[:]
    cmp = 0
    stack = [(0, len(a) - 1)]
    while stack:
        lo, hi = stack.pop()
        if lo >= hi:
            continue
        # 고른 피벗을 맨 끝으로 옮긴 뒤 나누기
        if pivot_mode == "mid":
            p = (lo + hi) // 2
        elif pivot_mode == "random":
            p = random.randint(lo, hi)
        else:
            p = hi
        a[p], a[hi] = a[hi], a[p]
        pivot = a[hi]
        i = lo
        for j in range(lo, hi):
            cmp += 1
            if a[j] < pivot:
                a[i], a[j] = a[j], a[i]
                i += 1
        a[i], a[hi] = a[hi], a[i]
        stack.append((lo, i - 1))
        stack.append((i + 1, hi))
    return a, cmp


random.seed(42)
n = 2000
inputs = {
    "랜덤": [random.randint(0, 100000) for _ in range(n)],
    "정렬됨": list(range(n)),
    "역순": list(range(n, 0, -1)),
}

print(f"n = {n}, 비교 횟수")
print(f"{'입력':<6} | {'끝 피벗':>10} | {'가운데 피벗':>10} | {'랜덤 피벗':>10}")
for name, data in inputs.items():
    _, c_end = quick_sort(data, "end")
    _, c_mid = quick_sort(data, "mid")
    _, c_rand = quick_sort(data, "random")
    print(f"{name:<6} | {c_end:>10,} | {c_mid:>10,} | {c_rand:>10,}")
```

```text
랜덤     |     54,053 |     54,499 |     53,784
```

- 표 읽는 법
  - 줄: 어떤 배열을 넣었는지
  - 칸: 피벗을 어디서 골랐는지
  - 숫자: 정렬이 끝날 때까지 한 비교 횟수
- 랜덤 입력
  - 셋 다 약 5.4만 번
  - 섞여 있으면 어느 자리를 골라도 피벗 값은 랜덤과 비슷
- 정렬됨 + 끝 피벗: 7,998,000번
  - 1번 섹션 버블 정렬 n = 4000과 한 자리까지 같은 숫자
  - 이 경우 퀵 정렬이 버블 정렬만큼 일함
- 정렬됨 + 가운데 피벗: 39,917번
  - 랜덤 피벗보다도 적음
  - 정렬된 배열은 가운데 자리 숫자가 곧 중앙값이라 매번 정확히 반씩 나뉨
- 역순도 같은 이유
  - 끝 피벗은 매번 가장 작은 값이 걸려서 최악
  - 가운데 피벗이 가장 적음

> 같은 배열, 같은 퀵 정렬인데 피벗 고르는 자리만 바꿔서 200배 차이

<Note type="warning" title="가운데 피벗의 약점">
- 어디를 고를지 미리 알 수 있음
- 가운데 자리에 일부러 큰 값을 넣은 배열을 만들면 다시 O(n²)
- 랜덤 피벗은 예측이 안 돼서 그런 배열을 만들 수 없음
- 그래서 실제 라이브러리는 "맨 앞, 가운데, 맨 끝 세 값 중 중간"이나 랜덤을 섞어 씀
</Note>

실무에서 정렬된 데이터는 생각보다 흔함

- ID 순서로 쌓인 데이터
- 시간순 로그

## 3. 삽입 정렬과 거의 정렬된 데이터

### 삽입 정렬

- 카드 게임에서 손에 든 카드 정리하는 방식
- 왼쪽은 정렬된 상태 유지
- 오른쪽에서 숫자를 하나 집어서 왼쪽에 들어갈 자리를 찾아 끼워 넣음
- 자리는 바로 왼쪽부터 하나씩 비교하며 찾음

`[3, 1, 4, 2]` 따라가기

```text
[3 | 1, 4, 2]   1을 집음 → 3과 비교, 더 작음 → 앞으로
[1, 3 | 4, 2]   (비교 1번)

[1, 3 | 4, 2]   4를 집음 → 3과 비교, 더 큼 → 그 자리
[1, 3, 4 | 2]   (비교 1번)

[1, 3, 4 | 2]   2를 집음 → 4보다 작음 → 3보다 작음 → 1보다 큼 → 멈춤
[1, 2, 3, 4]    (비교 3번)
```

처음엔 "숫자를 통째로 뒤로 보내는 것"으로 잘못 알고 있었음

- `[3, 1, 4, 2]` → `[1, 4, 2, 3]`처럼 3을 맨 뒤로 보내는 모양
- 실제로 통째로 밀리는 건 자리를 비켜주는 큰 숫자들

```text
[1, 3, 4 | 2]      2를 집음
[1, _, 3, 4]       3, 4가 한 칸씩 오른쪽으로 밀림
[1, 2, 3, 4]       빈자리에 2를 넣음
```

### 이미 정렬된 배열이면

```text
[1 | 2, 3, 4, 5]   2를 집음 → 1보다 큼 → 그대로   비교 1번
[1, 2 | 3, 4, 5]   3을 집음 → 2보다 큼 → 그대로   비교 1번
[1, 2, 3 | 4, 5]   4를 집음 → 3보다 큼 → 그대로   비교 1번
[1, 2, 3, 4 | 5]   5를 집음 → 4보다 큼 → 그대로   비교 1번
```

- 숫자마다 비교 1번, 밀리는 숫자 없음
- n개면 n - 1번 → O(n)
- 반대로 역순 `[5, 4, 3, 2, 1]`은 매번 맨 앞까지 → 1 + 2 + 3 + 4 = 10번, O(n²)

### 돌려보기

- 삽입 정렬과 병합 정렬 비교
- 거의 정렬: 정렬된 배열에서 이웃한 두 칸을 40번만 바꾼 배열

```python
import random


def insertion_sort(a):
    a = a[:]
    cmp = 0
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0:
            cmp += 1
            if a[j] <= key:
                break
            a[j + 1] = a[j]  # 큰 숫자를 한 칸 오른쪽으로 밀기
            j -= 1
        a[j + 1] = key
    return a, cmp


def merge_sort(a):
    if len(a) <= 1:
        return a, 0
    mid = len(a) // 2
    left, c1 = merge_sort(a[:mid])
    right, c2 = merge_sort(a[mid:])
    out, i, j, cmp = [], 0, 0, c1 + c2
    while i < len(left) and j < len(right):
        cmp += 1
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out += left[i:] + right[j:]
    return out, cmp


def nearly_sorted(n, swaps):
    # 정렬된 배열에서 이웃한 두 칸을 swaps번 바꿈
    a = list(range(n))
    for _ in range(swaps):
        k = random.randint(0, n - 2)
        a[k], a[k + 1] = a[k + 1], a[k]
    return a


random.seed(42)
n = 2000
inputs = {
    "정렬됨": list(range(n)),
    "거의 정렬 (40칸 섞음)": nearly_sorted(n, 40),
    "랜덤": [random.randint(0, 100000) for _ in range(n)],
    "역순": list(range(n, 0, -1)),
}

print(f"n = {n}, 비교 횟수")
print(f"{'입력':<16} | {'삽입':>10} | {'병합':>10}")
for name, data in inputs.items():
    _, ci = insertion_sort(data)
    _, cm = merge_sort(data)
    print(f"{name:<16} | {ci:>10,} | {cm:>10,}")
```

```text
정렬됨              |      3,999 |     23,728
거의 정렬 (40칸 섞음)   |      4,039 |     23,747
랜덤               |  3,968,289 |     42,796
역순               |  7,998,000 |     24,176
```

| 입력 | 삽입 | 병합 | 누가 적게 일했나 |
| --- | --- | --- | --- |
| 정렬됨 | 3,999 | 23,728 | 삽입 (약 6배 적음) |
| 거의 정렬 | 4,039 | 23,747 | 삽입 (약 6배 적음) |
| 랜덤 | 3,968,289 | 42,796 | 병합 (약 90배 적음) |
| 역순 | 7,998,000 | 24,176 | 병합 (약 330배 적음) |

- 정렬됨: 4000 - 1 = 3,999번
- 거의 정렬: 3,999번에서 딱 40번 늘어남
  - 섞인 칸마다 한 칸 앞으로 가면서 비교 1번씩 추가
- 역순: 매번 맨 앞까지 가서 버블과 같은 7,998,000번
- 랜덤: 역순의 절반쯤
  - 평균적으로 왼쪽 부분의 절반쯤 가면 자리를 찾음
- 병합은 어떤 배열이든 2만~4만 번

> 삽입 정렬은 정렬에 가까울수록 빨라지고, 섞여 있을수록 느려짐
> 병합 정렬은 데이터가 어떻든 항상 비슷함

예: 정렬된 회원 목록 1만 명에 신규 가입자 3명 추가 후 다시 정렬

- 삽입: 9,997명은 비교 1번씩, 새로 들어온 3명만 자리 찾기
- 병합: 이미 정렬돼 있어도 처음부터 다 쪼개고 합침
- 삽입 정렬이 유리

## 4. 파이썬 sorted()

### Timsort

- `sorted()`는 Timsort
- 완전히 새로운 알고리즘이 아니라 앞에서 본 것들의 조합
  - 런(run) 찾기: 앞에서부터 훑으며 이미 정렬된 구간을 찾음 (역순 구간은 뒤집어서 사용)
  - 삽입 정렬: 런이 너무 짧으면 삽입 정렬로 일정 길이까지 늘림
  - 병합 정렬: 런끼리 합침
- 구현이 C라서 같은 비교도 직접 짠 파이썬 코드보다 빠름

두 가지를 따로 확인

- 비교 횟수: 알고리즘 자체의 차이
- 시간: C 구현 효과까지 합친 실제 속도

`sorted()`는 안쪽이 C라 비교 횟수를 직접 셀 수 없음

- 비교할 때마다 횟수가 올라가는 포장 클래스 `Num`을 씌워서 셈

### 돌려보기

```python
import random, time


class Num:
    # sorted()가 비교할 때마다 횟수를 세기 위한 숫자 포장
    count = 0

    def __init__(self, v):
        self.v = v

    def __lt__(self, other):
        Num.count += 1
        return self.v < other.v


def sorted_count(a):
    Num.count = 0
    sorted(Num(x) for x in a)
    return Num.count


def merge_sort(a):
    if len(a) <= 1:
        return a, 0
    mid = len(a) // 2
    left, c1 = merge_sort(a[:mid])
    right, c2 = merge_sort(a[mid:])
    out, i, j, cmp = [], 0, 0, c1 + c2
    while i < len(left) and j < len(right):
        cmp += 1
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out += left[i:] + right[j:]
    return out, cmp


def nearly_sorted(n, swaps):
    a = list(range(n))
    for _ in range(swaps):
        k = random.randint(0, n - 2)
        a[k], a[k + 1] = a[k + 1], a[k]
    return a


random.seed(42)
n = 4000
inputs = {
    "정렬됨": list(range(n)),
    "거의 정렬 (40칸 섞음)": nearly_sorted(n, 40),
    "랜덤": [random.randint(0, 100000) for _ in range(n)],
    "역순": list(range(n, 0, -1)),
}

print(f"[1] n = {n}, 비교 횟수")
print(f"{'입력':<16} | {'병합(직접)':>10} | {'sorted()':>10}")
for name, data in inputs.items():
    _, cm = merge_sort(data)
    cs = sorted_count(data)
    print(f"{name:<16} | {cm:>10,} | {cs:>10,}")

print()
print("[2] 랜덤 숫자, 시간(초)")
print(f"{'n':>9} | {'병합(직접)':>10} | {'sorted()':>10}")
for n in [10_000, 100_000]:
    data = [random.randint(0, n * 10) for _ in range(n)]
    t = time.perf_counter(); merge_sort(data); tm = time.perf_counter() - t
    t = time.perf_counter(); sorted(data); ts = time.perf_counter() - t
    print(f"{n:>9,} | {tm:>10.4f} | {ts:>10.4f}")
```

비교 횟수

- 정렬됨: 3,999번
  - 처음부터 끝까지 하나의 런이라는 걸 알아채고 끝
  - 삽입 정렬과 같은 n - 1번
- 역순: 3,999번
  - 삽입 정렬은 여기서 7,998,000번으로 최악이었음
  - 통째로 역순인 런이라 뒤집기만 함 (뒤집기는 비교 불필요)
- 거의 정렬: 6,605번
  - 섞인 칸 때문에 런이 여러 조각으로 끊겨서 합치는 비교가 추가
  - 그래도 병합의 4분의 1 수준
- 랜덤: 42,609번
  - 직접 짠 병합과 거의 같음
  - 활용할 런이 없으면 결국 병합 정렬처럼 동작

- 이 차이는 알고리즘이 아니라 C 구현 효과
- 둘 다 O(n log n)이라 n이 커져도 배수가 일정함

> sorted()가 빠른 이유
>
> - 정렬된 구간이 있으면 알아채고 활용 → 비교 횟수 감소
> - C로 구현 → 같은 비교도 더 빠름

## 5. 어떤 정렬을 언제 쓰나

| 정렬 | 잘 맞는 상황 | 피해야 할 상황 |
| --- | --- | --- |
| 버블 | 개념 공부용 | 실제 데이터 전부 |
| 삽입 | 숫자가 적을 때 (수십 개)<br/>거의 정렬된 데이터에 몇 개 추가할 때 | 많고 섞인 데이터 |
| 병합 | 데이터 상태를 모를 때<br/>항상 일정한 속도가 필요할 때 | 메모리가 부족할 때 (합칠 때 새 배열 필요) |
| 퀵 | 메모리를 아껴야 할 때 (배열 안에서 자리만 바꿈) | 끝 피벗 + 정렬된 데이터 |

버블 정렬은 실무에서 거의 안 씀

- 같은 O(n²)인 삽입 정렬이 항상 더 나음
  - 랜덤 4000개 비교: 버블 7,998,000번, 삽입 3,968,289번 (약 절반)
  - 버블은 두 칸 맞바꾸기, 삽입은 한 칸씩 밀기라 쓰기 작업도 적음
- "한 바퀴 동안 바꾼 게 없으면 멈추기"를 넣으면 정렬된 데이터에서 n번으로 줄지만, 그건 삽입 정렬이 원래 하는 일
- 그래도 배우는 이유: 가장 단순한 정렬이라 O(n²)의 기준점 역할 (퀵 최악, 삽입 역순이 "버블과 같은 숫자")

- 실제로는 직접 고르기보다 언어 내장 정렬(`sorted()`, `Arrays.sort()` 등)을 씀
- 내장 정렬은 위 장점을 섞어서 만들어져 있음
- 그래도 알아두면 좋은 이유
  - 내장 정렬이 어떤 데이터에서 유리한지 이해 가능
  - "이미 정렬된 걸 활용하기", "최악의 경우 피하기"는 정렬 밖에서도 계속 나옴 (예: [DB 인덱스](/blog/db-index)도 정렬된 구조를 활용)

## 다시 설명

- **버블 정렬**
  - 옆 칸끼리 비교하며 큰 값을 뒤로
  - 숫자 2배 → 비교 4배, O(n²)
- **병합 정렬**
  - 반으로 쪼갠 뒤 정렬된 두 줄의 맨 앞끼리 비교하며 합침
  - 비교 한 번에 숫자 하나 확정, 단계 수는 log n
  - 숫자 2배 → 비교 약 2.2배, O(n log n)
- **퀵 정렬**
  - 피벗 기준으로 작은 쪽, 큰 쪽으로 나누기 반복
  - 반씩 나뉘면 O(n log n), 1개씩 줄면 O(n²)
  - 끝 피벗은 정렬된 배열에서 최악 → 가운데, 세 값 중 중간, 랜덤으로 피함
- **삽입 정렬**
  - 왼쪽 정렬된 부분에 하나씩 끼워 넣기
  - 정렬된 데이터는 O(n), 역순은 O(n²)
- **sorted() (Timsort)**
  - 정렬된 구간(런) 활용 + 삽입 정렬 + 병합 정렬
  - C 구현이라 같은 O(n log n)이어도 약 13배 빠름
