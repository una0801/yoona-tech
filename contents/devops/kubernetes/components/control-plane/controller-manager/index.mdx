## 개념
- kubernetes의 리소스들이 **원하는 상태와 실제 상태를 지속적으로 비교**하고 차이가 있으면 이를 **자동으로 조정**하는 백그라운드 루프
  - ex: 사용자가 deployment에 relicas : 3 이라고 선언 -> 실제 pod이 2개면? -> ReplicaSet Controller가 1개 더 생성해서 맞춤

  | 항목      | 내용                                    |
  | ------- | ------------------------------------- |
  | 위치      | Control Plane 구성요소                    |
  | 역할      | 리소스 상태 유지 (조정 루프)                     |
  | 동작 방식   | Watch → Reconcile → Patch             |
  | 주요 컨트롤러 | Deployment, ReplicaSet, Job, Node 등   |
  | 실무 영향   | 클러스터 안정성, 자가 복구, 자동 관리의 핵심            |
  | 확장성     | Custom Controller, Operator 개발로 확장 가능 |
- Controller 자체는 상태 저장 X : Stateless Process
  - 모든 상태는 etcd에 저장
  - 컨트롤러는 단지 현재 상태를 읽고 조정

## 작동원리
- 여러 개의 개별 컨트롤러들을 하나의 바이너리 프로세스로 실행
- 내부 동작 : 기술적/로직 중심
  ```
  1. Controller는 API Server로부터 리소스를 watch
  2. 변경 이벤트가 발생하면 WorkQueue에 추가
  3. Controller는 해당 리소스를 가져와 Reconcile 함수 실행
  4. 현재 상태와 원하는 상태 비교
  5. 수정이 필요하다면 -> API Server에 변경 요청
  ```
- 사용자 관점 : 시스템 전체의 작동 흐름
  ```
  1. 사용자가 YAML을 통해 리소스 생성 (ex: Deployment)
  2. API Server가 요청을 처리하고 etcd에 저장
  3. kube-controller-manager는 API Server를 통해 리소스 상태를 watch
  4. 원하는 상태와 실제 상태를 비교
  5. 차이가 있다면 -> kube-apiserver에 명령요청 (ex: Pod 생성)

  사용자 요청 -> etcd -> controller 감지 -> 조정
  ```

## 주요 내장 컨트롤러
| 컨트롤러 이름                          | 역할                    |
| -------------------------------- | --------------------- |
| **Node Controller**              | 노드 상태 감지, 장애 노드 탐지    |
| **Replication Controller**       | 지정된 수의 Pod를 항상 유지     |
| **ReplicaSet Controller**        | ReplicaSet 기반 Pod 유지  |
| **Deployment Controller**        | 배포 관리, 롤링 업데이트 수행     |
| **Job Controller**               | 일회성 작업(Pod) 실행 관리     |
| **CronJob Controller**           | 스케줄 기반 작업 실행          |
| **Namespace Controller**         | 네임스페이스 삭제 시 관련 리소스 정리 |
| **Service Account Controller**   | 새 네임스페이스에 기본 SA 자동 생성 |
| **Persistent Volume Controller** | PVC와 PV 매칭, 바인딩 처리    |

- **Deployment Controller**
  ```
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: nginx-deploy
  spec:
    replicas: 3
  ...
  ```
  - Deployment 리소스 생성
  - Controller가 이를 감지하고 ReplicaSet 생성
  - ReplicaSet Controller가 3개의 Pod 생성
  - Pod 가 죽으면 -> 다시 생성해서 항상 3개 유지
- **Node Controller**
  - 주거직으로 Node의 Heartbeat(상태보고)를 감지
  - 일정 시간 이상 응답 없는 Node -> NotReady 상태
  - 해당 노드에 있던 Pod를 다른 Node에 재배치 -> Self-healing
- **Job Controller**
  - 지정된 Pod가 한번 실행되고 정상 종료되면 완료 상태로 유지
  - 실패하면 다시 실행
  - Pod가 정상적으로 `exit code 0`을 반환해야 성공으로 간주

## 작동 원리
- ex: 사용자가 `kubectl apply -f nginx.yaml` 실행
  1. API Server가 요청을 받아 유효성 검사 -> Admission Controller 통과
  2. 리소스 오브젝트를 etcd에 저장
  3. kube-controller-manager, scheduler 등을 watch로 etcd 변경 감지
  4. 필요한 동작 수행(ex: Pod 생성 -> kubelet -> containerd)
- etcd는 watch API를 제공하여 변경 이벤트를 실시간으로 API Server에 전달
