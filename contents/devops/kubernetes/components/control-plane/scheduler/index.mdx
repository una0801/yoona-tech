## 개념
- 새로 생성된 pod가 어느 노드에 배치될지를 결정하는 핵심 컴포넌트
  | 항목     | 내용                            |
  | ------ | ----------------------------- |
  | 역할     | Pod를 적절한 Node에 배치             |
  | 위치     | Control Plane 구성요소            |
  | 입력     | Pending 상태의 Pod               |
  | 출력     | Pod에 `.spec.nodeName` 할당      |
  | 주요 단계  | Filtering → Scoring → Binding |
  | 확장성    | Plugin 기반 스케줄러 확장 가능          |
  | 실무 중요성 | 성능, 자원 분산, 안정성에 직접 영향         |
---
## 주요 기능
| 기능                 | 설명                                            |
| ------------------ | --------------------------------------------- |
| Pending 상태의 Pod 감지 | 아직 Node에 할당되지 않은 Pod 감시                       |
| 노드 리스트 수집          | 클러스터의 모든 노드 상태 수집 (리소스, 조건 등)                 |
| 노드 후보 필터링          | 특정 조건을 만족하는 Node만 추림 (Filtering)              |
| 점수 계산 및 정렬         | 가장 적합한 Node를 우선순위로 정렬 (Scoring)               |
| 최종 배치 결정           | 가장 점수가 높은 Node를 선택하여 Pod에 `.spec.nodeName` 할당 |
                                  |

## 작동 흐름
- 전체
```
1. 사용자가 deployment 또는 Pod 생성
2. API Server -> etcd 저장 -> Pod 상태는 "Pending"
3, kube-scheduler가 pending pod 을 감지 (Watch)
4. 스케줄링 알고리즘 수행 (Filter -> Score -> Select)
5. Pod의 .spec.nodeName 에 node 이름 할당
6. kubelet이 그 pod 을 감지하고 컨테이너 실행
```
- 세부
  1. **Pod 감지 (Watch)**
   - scheduler는 API Server를 톨해 pending 상태의 pod만 실시간 감지
   - 새로운 pending이 생기면 WorkQueue에 추가되어 처리 대상이 됨
  2. **노드 리스트 가져오기**
   - API Server에서 현재 클러스터에 있는 모든 Node의 상태를 조회
   - 각 Node 의 :
     - CPU / Memeory 등 리소스 여유량
     - Taint / Toleration 정보
     - Pod 할당 여부
     - 상태 조건 (Ready 등)
     등을 수집
  3. **Filterting (Predicates)**
    - Pod을 배치할 수 없는 노드는 제거 (하드조건) 
    - 결과적으로 후보 노드 리스트가 생성됨
    - 예시 조건 :
      | 필터 조건                | 설명                                 |
      | -------------------- | ---------------------------------- |
      | Node Unschedulable   | 노드가 스케줄링을 막아둔 경우                   |
      | PodFitsResources     | CPU, Memory 부족                     |
      | NodeAffinity         | NodeSelector, Node Affinity 조건 불일치 |
      | Taints & Tolerations | Taint가 있는데 Toleration이 없음          |
      | PodTopologySpread    | 토폴로지 분산 조건 미충족                     |

  4. **Scoring (Priorities)**
    - 후보 노드 마다 점수를 계산하고 가장 적합한 Node를 선택
    - 0 ~ 100점의 스코어로 각 노드를 평가
    - 가장 점수가 높은 노드가 선택 (동점이면 랜덤)
    - 기본 우선순위 예시:
      | 점수 기준               | 설명                     |
      | ------------------- | ---------------------- |
      | Least Requested     | 리소스 여유가 많은 Node 우선     |
      | Balanced Allocation | CPU/메모리 비율 균형          |
      | Topology Spread     | 분산 배치 고려               |
      | Image Locality      | 필요한 이미지를 미리 가진 Node 우선 |
  5. Binding (할당)
    - 최종 선택된 Node의 이름을 Pod의 `.spec.nodeName` 필드에 할당
    - `Bind` API 호출로 API Server Update
    - 이 후 kubelet이 그 Pod를 감지하고 실행 시작

## 아키텍퍼
- plugin 기반 구조이기떄문에, 자체적으로 스케줄링 정책을 확장하거나 변경하는 것이 가능
  ```
  [Pod Queue] → [Scheduling Cycle]
                        ↓
                  [Filtering Plugins]
                        ↓
                  [Scoring Plugins]
                        ↓
                  [Node Selection]
                        ↓
                    [Binding]

  ```

## 고급기능
1. **Taint & Tolerations**
  - 특정 Node에 Pod가 배치되지 않도록 Taint 설정
  - Pod가 Toleration을 가지면 해당 Taint를 무시하고 배치 가능
    ```
    tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"
    ```
2. **Node Affinity / Pod Affinity**
   - 특정 Node 조건 또는 Pod 조건을 만족하는 곳에만 배치하도록 설정
    ```
    affinity:
      nodeAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
          nodeSelectorTerms:
          - matchExpressions:
            - key: "zone"
              operator: "In"
              values:
              - us-east-1a
    ```
3. **Topology Spread Constraints**
   - 동일한 레이블의 Pod가 Node 또는 Zone 단위로 고르게 분산되도록 설정
     ```
     topologySpreadConstraints:
     - maxSkew: 1
       topologyKey: "topology.kubernetes.io/zone"
       whenUnsatisfiable: ScheduleAnyway
       labelSelector:
         matchLabels:
           app: web
     ```

## 디버깅 및 모니터링
- 스케줄 상태 확인
  ```
  kubectl describe pod <pod-name>
  

  Events:
  Type     Reason             Message
  ----     ------             -------
  Warning  FailedScheduling   0/3 nodes are available: 3 Insufficient memory.
  ```
- 스케줄러 로그 확인
  ```
  kubectl logs -n kube-system kube-scheduler-<node-name>
  ```

## 커스터마이징
- custom scheduler 개발 가능
- kube-sceduler 바이너리를 수정하지 않고도 policy, plugin, webhook 으로 확장 가능
- 여러 스케줄러를 병렬로 사용 가능 (schedulerName 필드 사용)
  ```
  apiVersion: v1
  kind: Pod
  spec:
    schedulerName: custom-scheduler
  ```
