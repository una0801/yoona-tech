## 개념
- kubernetes 클러스터와 **외부(또는 내부)간의 모든 통신을 처리**하는 핵심 관문
- 클러스터의 요청은 반드시 이곳을 거쳐야하며, **상태저장, 리소스 조작, 인증 및 권한 검증**을 수행
  | 항목    | 내용                                        |
  | ----- | ----------------------------------------- |
  | 위치    | Control Plane 내부                          |
  | 핵심 역할 | 클러스터의 단일 진입점, 상태 변경 처리                    |
  | 핵심 기능 | 인증, 권한 검사, 상태 저장, Admission Control       |
  | 특징    | REST API, 무상태, 고확장성, 이벤트 중심 처리            |
  | 연동 대상 | kubectl, kubelet, scheduler, controller 등 |
---
## 주요 기능
| 기능                        | 설명                                        |
| ------------------------- | ----------------------------------------- |
| **RESTful API 제공**        | 모든 클러스터 객체를 CRUD하는 REST 인터페이스             |
| **클라이언트 입출력 처리**          | `kubectl`, Helm, 컨트롤러 등 외부/내부 클라이언트 요청 수신 |
| **Authentication (인증)**   | 사용자 또는 서비스 계정의 신원 확인                      |
| **Authorization (권한 확인)** | RBAC 등 정책 기반 권한 검사                        |
| **Admission Control**     | 객체 생성/변경 시 동적 정책 적용                       |
| **etcd와 통신**              | 모든 상태 정보를 etcd에 저장하거나 읽어옴                 |
| **Watch 기반 이벤트 전달**       | 컨트롤러 및 스케줄러 등 클러스터 내부 구성요소에 이벤트 전달        |

---
## 구성 흐름
```
[Client 요청]
     ↓
[Authentication] → 사용자 인증
     ↓
[Authorization] → 권한 검사 (RBAC, ABAC 등)
     ↓
[Admission Controller] → 정책, 리밋, 변형 적용
     ↓
[Validation & Mutation]
     ↓
[etcd 저장] 또는 [조회]
     ↓
[응답 반환]

```

## 인증
- 요청을 보낸 주체의 신원(identity) 확인
- `user`, `groups`, `UID` 등의 정보가 요청에 포함됨
  | 인증 방식                    | 설명                                        |
  | ------------------------ | ----------------------------------------- |
  | **X.509 인증서**            | 사용자 인증서 (kubectl 사용 시 client-certificate) |
  | **Bearer Token**         | Service Account Token 또는 OAuth 기반 토큰      |
  | **Static Token File**    | 미리 정의된 토큰을 사용하는 방식 (Deprecated)           |
  | **OIDC(OpenID Connect)** | 기업 인증 시스템 (SSO)와 연동 가능                    |
---
## 권한 검사
- 인증된 사용자라 하더라도 리소스에 접근할 수 있는지 별도로 검증
- `kubectl auth can-i` 명령어로 권한 확인 가능
  | 방식                                   | 설명                                    |
  | ------------------------------------ | ------------------------------------- |
  | **RBAC (Role-Based Access Control)** | 가장 많이 사용됨. `Role`, `RoleBinding`으로 제어 |
  | **ABAC (Attribute-Based)**           | YAML 파일로 속성 기반 권한 정의 (구식)             |
  | **Webhook Authorization**            | 외부 시스템과 통합된 정책 처리                     |
---
## Admission Controller
- 인증과 권한을 통과한 요청에 대해 **정책 적용, 검증, 변경을 수행**하는 플러그인
- Mutating -> Validating 순서로 실행
  | 타입                                  | 설명                |
  | ----------------------------------- | ----------------- |
  | **MutatingAdmissionWebhook**        | 객체를 변경(변형)하는 역할   |
  | **ValidatingAdmissionWebhook**      | 유효성 검사만 수행        |
  | **LimitRanger, ResourceQuota**      | 리소스 제한 적용         |
  | **PodSecurity, NamespaceLifecycle** | 보안 및 네임스페이스 관리 정책 |
---
## etcd와의 상호작용
- API Server는 클러스터 상태를 etcd에 저장하거나 조회
  - 상태 변경 요청(ex: `kubectl apply`) -> etcd에 새로운 리소스 객체 저장
  - 조회 요청(ex: `kubectl get`) -> etcd로부터 읽기
  - watch 기반 변경 이벤트는 etcd -> API Server -> Controller/Scheduler로 전달
    ```
    # 예시 저장 키
    /registry/pods/default/nginx
    /registry/services/kube-system/kube-dns
    ```

## 내부 통신
- 클러스터 내부 컴포넌트들과 연결
  | 컴포넌트               | 연결 목적                    |
  | ------------------ | ------------------------ |
  | kubelet            | 노드 상태 수집, Pod 상태 전달      |
  | controller-manager | 상태 조정 정보 제공              |
  | scheduler          | Pending Pod 제공, 배치 요청 수신 |
  | webhook 서버         | 정책 유효성 검사 위임             |
- 내부 컴포넌트들도 모두 API Server를 통해서만 접근
  (ex: kubelet이 pod 상태 보고 -> API Server에 POST)

## 경로 구조
- RESTful 구조로 되어있으며 대부분 CRUD 형식에 맞춰 동작
  | 리소스            | 경로 예시                                            |
  | -------------- | ------------------------------------------------ |
  | Pod 목록         | `/api/v1/namespaces/default/pods`                |
  | Deployment 생성  | `/apis/apps/v1/namespaces/default/deployments`   |
  | CustomResource | `/apis/<group>/<version>/namespaces/<ns>/<kind>` |
---
## Group과 Version
- 다양한 리소스를 API Group으로 나눔
- 이를 통해 버전관리, 확장성, 커스텀 리소스 정의(CRD)등을 지원
  | Group                     | 예시 리소스                             |
  | ------------------------- | ---------------------------------- |
  | core (`/api/v1`)          | Pod, Service, Namespace, ConfigMap |
  | apps (`/apis/apps/v1`)    | Deployment, StatefulSet, DaemonSet |
  | batch (`/apis/batch/v1`)  | Job, CronJob                       |
  | rbac.authorization.k8s.io | Role, RoleBinding, ClusterRole     |

## 확장성과 고가용성
- 스케일 아웃 가능 : API Server는 무상태(Stateliess) 서비스 -> 여러 인스턴스로 확장 가능
- HA 구성 : 로드밸런서 앞에 API Server 여러 대 + Shared etcd 구성
- 인그레스 대신 직접 접근 : 보통 내부/관리 트래픽은 LB(ex:ELB, NLB) 통해 전달
